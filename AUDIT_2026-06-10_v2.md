## Phase 2 — Findings by Severity

### 🔴 HIGH

**H1 — The local working tree is corrupted; the checkout cannot build. (verified, data-loss class)**
~25 files — exactly the set rewritten by today's fix session — were written in place without truncating to the new length, leaving stale-byte/NUL tails: `app/src/MagicNumberAppMain.jsx` contains 14,706 NUL bytes; `app/src/hooks/useFinancialEngine.js` ends mid-identifier (`…bSR, bNW, per`); `app/src/utils/financial.js` ends mid-comment (`/** Future value with variabl`); **`app/package.json` is truncated at line 21 mid-string (`"@vitej`)**, which alone breaks `npm run dev/build/test` on this machine. esbuild syntax-check: HEAD = 0 failures across 46 files; working tree = unbuildable. Recovery is one command — `git restore .` (plus `git clean` for `.netlify/`) — and is **safe**: I diffed working tree vs HEAD ignoring whitespace/CRLF; the only differences are the corruption itself, no uncommitted work exists. Inference as to cause: a file-writing tool that overwrote without truncate; the commit content was staged from buffers, so git never saw the damage. Production is unaffected (CI builds from the pushed commit).

**H2 — Email-gate leads land in the analytics table, fire-and-forget, failures silently swallowed. (verified)**
The fix for the old "emails captured nowhere" bug routes the email through analytics: `track(EVENTS.EMAIL_SUBMITTED,{email:userEmail},…)` at `app/src/tabs/AchieveTab.jsx:180` and `app/src/tabs/InactionTab.jsx:189`. That means: (a) lead emails live in `analytics_events.props` (jsonb) — not in `leads`, where a human advisor actually looks; (b) delivery is batched with a 5s timer (`app/src/utils/analytics.js:24`) and the insert error path is deliberately swallowed with no retry (`analytics.js:42-46`, comment: "analytics should never block the app" — correct for analytics, wrong for the product's only revenue-adjacent asset); (c) if Supabase env vars are missing the email is logged to console in dev and discarded in prod (`analytics.js:32-39`). For a pre-launch product whose ROADMAP counts "Leads: 2 (test)", every silently-lost email is invisible damage. The tier flip itself (`setTier("email")`) works; capture is the fragile half.

**H3 — Monetization is a stub while the UI sells it. (verified)**
"Full access — $14.99" buttons at `app/src/tabs/AchieveTab.jsx:195` and `:333` fire `alert("Stripe coming soon!")`. Meanwhile `tasks/todo.md` (W17, decision D2) specifies a **$3.99 micro-payment** and MercadoPago investigation — UI price and decided price disagree by 4×. Tier state is purely client-side (`localStorage`, `?demo=1` at `MagicNumberAppMain.jsx:29`) — fine today since there's nothing to steal, but any future Stripe integration must move entitlement server-side or the paywall is decorative.

### 🟡 MEDIUM

**M1 — 9 of 15 analytics events never fire; the funnel is unmeasurable. (verified)**
Call-site count across src: `LANDING_ENTERED_APP`, `PAGE_VIEW`, `PAYWALL_VIEWED`, `TIER_CHANGED`, `MAGIC_NUMBER_CALCULATED`, `SCORE_VIEWED`, `DEMO_MODE_ENTERED`, `DATA_CLEARED`, `CTA_CLICKED` = **0 call sites each** (defined in `app/src/utils/analytics.js:119-135`). `LandingPage.jsx` contains zero `track()` calls — the landing→app conversion, the single most important number for a freemium pre-launch product, is not recorded. ROADMAP scores Analytics 8.5/10; actual coverage is ~40% of the designed schema, with the top of the funnel dark.

**M2 — EngineContext exists, is provided, and nothing consumes it. (verified)**
`app/src/hooks/EngineContext.jsx` defines `useEngine()`; Main wraps everything in `<EngineProvider value={ctx}>` (`MagicNumberAppMain.jsx:107`) — and every tab still receives `engine` as a prop (`MagicNumberAppMain.jsx:133-148`); `grep useEngine` across tabs: zero hits. The commit message ("eliminate god component prop-drilling" via context) and ROADMAP architecture diagram describe a design that isn't wired. Cosmetic in behavior, but the project's written self-description has drifted from the code on day one of the new architecture. Related: `MagicNumberAppMain.jsx:44` destructures `magicRevealed` from the engine, which the engine does not return — always `undefined`, shadowed by the correct `store.magicRevealed` at line 51.

**M3 — Whole-store subscriptions: every keystroke re-renders the app and re-runs the engine. (verified)**
Main (`MagicNumberAppMain.jsx:32`) and at least 8 tabs call `useAppStore()` with no selector; any field change re-renders all mounted components and recomputes `useFinancialEngine`. Tolerable at current size (engine internals are memoized), but it's the scaling cliff. The codebase already contains the correct pattern: `app/src/components/AdvisorCTA.jsx:5-6` uses per-field selectors.

**M4 — Unthrottled anonymous inserts + PII sprawl across two tables. (verified)**
`WITH CHECK (true)` for anon INSERT on both `leads` (`app/supabase/leads-table.sql:58`) and `analytics_events` (`analytics-table.sql:22`), no rate limiting, no captcha — anyone with the public URL+key can spam both tables (junk in the advisor pipeline, quota burn). H2 makes it worse: emails now exist in `analytics_events.props` too, so PII deletion/retention requires touching two tables. RLS read-side is correct (no anon SELECT — verified, good).

**M5 — Dual deploy configs; the dead one still carries a security policy. (verified)**
`app/netlify.toml` duplicates the CSP/headers that actually ship via `app/public/_headers` on Cloudflare Pages. Next person to edit headers will plausibly edit the Netlify copy and see no effect. `.netlify/` exists untracked on disk; `_redirects` equivalent for SPA routing on CF Pages should be confirmed — *inference: I could not verify CF Pages SPA-fallback config in the repo (no `_redirects` file found); if deep links 404 in production, this is why.*

**M6 — Two i18n systems. (verified)**
A real dictionary system (`app/src/i18n/`, ~765 keys/lang) coexists with **58** inline `lang==="en"? … : …` ternaries across JSX (counted). Every copy change is a two-system hunt; the W36/W37 landing-copy fixes pending in todo.md are exactly this class of work.

## Leverage Points

1. **`git restore .` is worth more than any refactor today.** The highest-value change in the entire repo is one command that makes the local checkout match the healthy, tested, deployed HEAD (H1). Until then, every local edit session starts from corrupted files, and the next `git add -A && git commit` would **commit the corruption over today's fixes** — that's the real landmine.

2. **Wire the 9 dead analytics events — start with `LANDING_ENTERED_APP` in `LandingPage.jsx`'s `onEnter` and `MAGIC_NUMBER_CALCULATED` in the engine.** The schema, batching, table, and RLS all exist and work; the missing piece is ~9 one-line `track()` calls. For a pre-launch freemium product, this converts the existing infrastructure into the ability to answer "where do users drop off?" — the question every coming decision (pricing, copy, tab order) depends on.

3. **Move email-gate capture from `track()` to `submitLead()`** (or a dedicated `email_leads` insert with retry + user-visible failure). One function call swap at `AchieveTab.jsx:180` / `InactionTab.jsx:189` puts the product's only asset in the table humans actually read, with an error path that isn't swallowed (H2). While there, extract the twice-duplicated inline regex+track+setTier block into one `submitEmailGate()` helper.

4. **Either wire `useEngine()` into the 16 tabs or delete EngineContext.** Two-hour job. As-is (M2), the documented architecture and the real one diverged on day one, and the next contributor will trust the ROADMAP diagram. Wiring it also removes the `engine` prop plumbing and pairs naturally with adopting AdvisorCTA's selector pattern (M3) — the two changes together future-proof rendering performance.

5. **`utils/financial.test.js` is the protection pattern — extend it to `useFinancialEngine` before touching the engine again.** The 40 tests cover the primitives but not the orchestration layer where the past bugs actually lived (hard-coded rates, profile-index mixups, SS handling). The engine is a pure function of `(store, t, lang)` — snapshot-testing `magic`, `monthlyNeeded`, and `hScore` for 3 canned personas is an afternoon and would have caught most of this year's financial findings.

## Product & Strategy

**What's undervalued: the engine's honesty is the moat, and it's invisible.** This codebase computes in real (inflation-adjusted) terms, models tax drag, debt-payoff cash-flow events, scenario spreads, and annuity-to-zero retirement — meaningfully more rigorous than typical "retirement calculator" lead magnets, and now backed by tests. But the UI presents conclusions, not credibility: nothing on the landing or in the free tier says *why this number is trustworthy*. A "how we calculate" page (the methodology already written in code comments) would differentiate against every black-box competitor and directly serve the advisor-trust funnel. The builders score "Motor Financiero 9.5/10" internally and then hide it from users.

**The obvious gap a user will hit: language-market mismatch.** The product speaks rioplatense Spanish to an Argentina audience (per D2) while benchmarking them against US Federal Reserve-style net-worth percentiles and recommending FDIC CDs and TLT (L3). An Argentine user with savings in USD under a 100%+ historical-inflation context will find "2.5% inflation" and "your percentile: 75th" not just irrelevant but credibility-destroying — for precisely the audience the lead-gen funnel targets. Either commit to "planning in USD for Latin Americans" explicitly (a genuinely strong positioning — nobody serves it well) or localize the benchmarks. The half-measure is the worst option.

**The funnel design is better than its instrumentation.** Free MN-range → email for exact number → $X for 16 modules → human advisor handoff is a coherent ladder, and the lead record (full financial snapshot attached to contact info) is exactly what an advisor wants. But the price says $14.99 in the UI and $3.99 in the decision log (H3), the top-of-funnel is unmeasured (M1), and email capture is fire-and-forget (H2). The strategy work is done; the execution gaps are all small and mechanical. *Inference:* given "Users: 0 (pre-launch)" in ROADMAP, fixing measurement before driving traffic costs nothing and saves a wasted launch.

**Positioning insight the code reveals:** the strongest emotional asset isn't the magic number — it's the **Cost of Inaction** tab (free tier, dedicated module, the only concept with a named tab and an email gate of its own). "Waiting costs you $X/year" is the sharpest hook in the product and appears nowhere on the landing page, which leads with the generic "discover your number."

## Summary Verdict

The committed codebase is in the best shape of its life — today's five commits resolved essentially all of the prior audit (verified: 40/40 tests pass, clean build, dead code gone, funnel bugs fixed), and the architecture is now a thin router over a tested engine. The single most important finding is that **the local working tree is corrupted post-commit (H1): ~25 files including package.json are NUL-padded/truncated, the checkout can't build, and one careless `git commit -A` would overwrite today's fixes with garbage** — while the fix is a one-line `git restore .` because HEAD and origin are healthy. Second priority: lead emails route through a fire-and-forget analytics queue into the wrong table (H2). With 2 hours I would run `git restore . && git clean -fd app/.netlify && npm run build` to re-establish a sane local state (15 min), swap the email gate to a direct, error-checked `leads` insert (45 min), and add the missing `track()` calls for landing-entry and MN-calculation (30 min) — leaving 30 minutes to delete or wire EngineContext so the documentation stops lying about the architecture.
