# MaNu PRO — Technical Audit (Phases 1 & 2)

**Date:** 2026-06-10 · **Scope:** Discovery & Mapping + Audit (no improvement plan, per instructions) · **Calibration:** Hibernated MVP — findings weighted by what matters *if reactivated*, not enterprise standards.

---

## Phase 1 — Discovery & Mapping

### Inventory

~7,000 lines of source (excluding dist/ and lockfile). Largest files: i18n dictionaries (en.js 765 / es.js 764 lines — near-perfect parity, good), LandingPage.jsx (492), useFinancialEngine.js (390), index/landing CSS (387/839), AchieveTab.jsx (345), MagicNumberAppMain.jsx (317), useAppStore.js (268). The 15 reusable components are all small (17–86 lines) and clean.

### Data flow

```
useAppStore (Zustand + persist → localStorage "manu-pro-state")
        │ whole-store subscription
        ▼
MagicNumberAppMain ── useFinancialEngine(store) → ~80 computed values
        │
        ├─ legacy pattern (13 tabs): 20–40 individual props each
        └─ new pattern (AchieveTab, InactionTab): receives `engine` object,
           reads store directly via useAppStore()
```

Two prop-passing generations coexist. `refactor.cjs` in app/ is the leftover codemod that migrated AchieveTab/InactionTab to the new pattern — the migration stopped halfway through the 16 tabs.

### Repo state (notable for a hibernated project)

The working tree is **dirty**: 7 source files modified but uncommitted (MagicNumberAppMain, LeadCaptureModal, AchieveTab, DebtsTab, InvestTab, RetirementTab, SituationTab, vite.config). If the machine is lost, the hibernated snapshot loses work. `dist/` is committed to git. Two one-off codemod scripts (`clean_lines.cjs`, `refactor.cjs`) live in app/.

### Tab/module map

`constants.js` TABS defines 15 entries. DashboardTab exists as a 16th module but is **not in TABS** — see finding A4. Free tier: achieve, inaction, learn. Gating is purely client-side (`tier` in localStorage; `?demo=1` grants paid).

## Phase 2 — Audit Findings

Severity: 🔴 High (broken behavior / business impact) · 🟡 Medium (real defect, limited blast radius) · ⚪ Low (worth knowing).

### A. Business-critical functional bugs

These outrank architecture for a lead-gen product.

**🔴 B1 — The email gate captures nothing.** The free-tier funnel's primary conversion ("enter your email → reveal your exact Magic Number", AchieveTab.jsx:183, InactionTab.jsx:188) writes the email **only to the user's own localStorage** (`setTier("email")`). It is never sent to Supabase, no `submitLead` call, and the `EMAIL_SUBMITTED` analytics event defined in analytics.js is never fired anywhere. Every email "captured" since launch is unrecoverable. The only working lead channel is the advisor modal (LeadCaptureModal → `leads` table). If the project is reactivated, this is the first thing to fix.

**🔴 B2 — Broken email regex in InactionTab.** AchieveTab validates with `/^[^\s@]+@[^\s@]+\.[^\s@]+$/` (correct); InactionTab drifted to `/^[\S@]+@[\S@]+\.[\S@]+$/`, which accepts `@@@.@` (verified). Same validation duplicated a third time in LeadCaptureModal. Classic copy-paste drift with no shared utility.

**🔴 B3 — Dashboard tab is orphaned.** `goTab("dashboard")` fires once on upgrade-to-paid (MagicNumberAppMain.jsx:58) and DashboardTab renders, but "dashboard" is missing from `TABS` in constants.js, so it has no nav button — a paid user who navigates away can never return. The disabled-check at line 230 still references `tb.id!=="dashboard"`, suggesting it was accidentally dropped from TABS. The upgrade toast promises "all 16 modules"; nav shows 15.

**🟡 B4 — Duplicate-ID bug in expenses/debts/goals.** MagicNumberAppMain keeps ID counters in `useRef(store._nEId)` and increments the ref (line 180), but never writes back to the persisted `_nEId`. The store's own `addExpense` (which does it correctly) is dead code. Reproduction: add an expense (id 6 assigned, persisted counter stays 6) → reload (ref re-initializes to 6) → add another expense → two rows with id 6 → React key collision, and editing one edits both. Same pattern for debts (`_nDId`) and goals (`_nGId`).

**⚪ B5 — Payments are a stub.** The $14.99 button shows `alert("Stripe coming soon!")`. Known, but worth recording: the `paid` tier is reachable only via `?demo=1` or manual localStorage editing.

### B. Architecture & state management

**🟡 AR1 — The god component is now mostly dead weight, and that's the good news.** Lines 36–153 of MagicNumberAppMain are ~115 `const x = store.x; const setX = v => sf('x', v);` pairs that exist for "backward compatibility with existing JSX." The component itself does little real work. The cost is concrete, though: `useAppStore()` without selectors subscribes to the entire store, every setter wrapper is recreated each render, and the engine recomputes on any state change — so **every keystroke in any input re-renders the whole app and re-runs all financial math**. At this app's size that's tolerable (the engine is heavily memoized internally), which is why it works in production. On reactivation, finishing the AchieveTab-style migration (pass `engine`, read store directly) deletes most of this file.

**🟡 AR2 — Half-finished refactor left two parallel systems.** Store has CRUD helpers (`updateExpense/addExpense/removeDebt/goTab`...) that are entirely unused — Main reimplements them inline (with the B4 bug). Goal limit is 8 in the store helper, 10 in Main's. New-goal default `profileIdx` is 3 in INITIAL_STATE, 4 in both add-helpers. `DEFAULT_EXP` exists twice (constants.js and useAppStore.js) with different names *and different `discretionary` flags* — Transport is discretionary in one, not the other, which changes what the Save tab offers to cut. The store's copy wins (constants' is dead), but it's a trap.

**⚪ AR3 — Store design is otherwise solid.** Persist with explicit `PERSISTED_FIELDS` partialize, schema versioning, and a defensive merge that sanitizes corrupted localStorage (array checks, index clamping, tier whitelist) — this is better than typical MVP code. Two nits: UI-transient state (showLeadModal, emailError, tab) lives next to domain data; and the merge clamps profile indices to max 5, which silently un-selects a custom profile (index 6 in `allProfiles`) after reload.

**⚪ AR4 — Prop drilling is wide but shallow.** SituationTab takes ~33 props, RetirementTab ~35, DebtsTab ~38. One level deep only, so it's verbose rather than dangerous. The `engine` object pattern already proven in AchieveTab is the fix.

### C. Financial correctness

The core model — everything computed in real (inflation-adjusted) terms, magic number as PV of a monthly annuity over `yearsPostRet` plus discounted legacy — is sound and internally documented. Spot-check: $3,000/mo for 25y at 4% real → $572,632, correct for annuity-to-zero (more conservative assumptions than the 4%-rule heuristic would yield, by design via the `conservative` variant).

**🔴 F1 — `profByHorizon` (utils/financial.js:37) is broken: `PROFILES[6]` is undefined** for horizons ≥10y (array has 6 entries, indices 0–5), and the index mapping skips Treasuries entirely (y=2.5 → "6040"). It would crash on `.effReal` access — it's saved only by being dead code (the engine has its own correct `adjProfByHorizon` keyed by id). Delete it; if anyone ever imports it, it's a crash.

**🟡 F2 — Hard-coded 4% returns ignore the user's settings.** Save-tab opportunities, Earn projections, combined impact, and the health score's retirement-progress component all use literal `0.04` (engine lines 235, 246–248, 256–257, 356, 361) — not the user's selected profile, not tax-adjusted, not the `RET_NOM` constant that exists for exactly this and is never imported. A user invested at 6.5% real sees Save/Earn impact numbers inconsistent with every other tab.

**🟡 F3 — Two compounding conventions disagree by ~2%.** `fvC`/`pvA` compound monthly; `fvVariable`/`yearByYear` apply annual growth with end-of-year contribution lumps. Verified: $500/mo, 5%, 30y → $407,688 (fvC) vs $398,633 (fvVariable). `monthlyNeeded` mixes both *within one calculation* (projection annual, gap-filling annuity monthly). Small magnitude, but the "monthly needed" figures are slightly overstated and the charts won't exactly reconcile with the headline numbers.

**⚪ F4 — Tax model is a flat drag, not a tax.** `effReal = nomReturn − inflation − assetTax` subtracts percentage points. As an "annual wealth tax / expense ratio" slider (capped at 3%) this is defensible, and the UI tooltip frames it that way; just note it cannot represent capital-gains-style taxation. Similarly, real return uses the additive approximation rather than Fisher — ~0.2pp error at these magnitudes, fine.

**⚪ F5 — Drawdown coverage off-by-one.** The depletion loops (engine revResult line 331; duplicated twice in AchieveTab) count the year the balance goes negative as a full covered year — coverage overstated by ≤1 year.

**⚪ F6 — Return assumptions are reasonable.** 9% nominal equities, 6.5% real, 2.5% inflation, ±2% scenario spread — slightly optimistic on equities-real vs. long-run history but well within convention. The static `realReturn` values in constants.js PROFILES are ignored (engine recomputes from `customInflation`) — correctly so, but they're misleading dead data, and they drift when a user changes inflation. Note the audience mismatch: US-centric instruments (FDIC CDs, TLT, S&P) and US net-worth benchmarks, with an Argentina-default Spanish UI (+54 phone placeholder). Benchmark percentiles are presented to ES users against US data.

**⚪ F7 — Free-tier range comment drift.** Comment says "0.75×–1.30× + $50K rounding"; code does 0.85×/1.15× rounded to $25K. Code is fine; comment lies.

### D. Security & PII

**Posture is good for what it is.** Verified: the anon key is a new-style `sb_publishable_` key (safe to ship client-side); `.env` is not tracked in git; RLS on both tables is INSERT-only for anon with no SELECT policy, so leads/analytics cannot be read or enumerated from the client; CSP is strict (`default-src 'self'`, connect-src limited to the Supabase host, no inline scripts) and duplicated correctly in netlify.toml and `_headers`, plus HSTS/frame-deny/etc. This is above-average for an MVP.

**🟡 S1 — `.env` is one mistake away from git.** app/.gitignore does not list `.env` (only `*.local`). It's untracked today purely by discipline. Add `.env` to .gitignore — one line, do it even while hibernated.

**🟡 S2 — Unthrottled anonymous inserts.** `WITH CHECK (true)` on both tables with no rate limiting or captcha means anyone with the (public) URL+key can spam `leads` and `analytics_events` — junk in the advisor pipeline and Supabase quota burn. For a hibernated product with a human reviewing leads, low practical risk; on reactivation consider a length/shape CHECK constraint and Supabase's built-in rate limits or a captcha on the modal.

**⚪ S3 — The leads table is a honeypot by design.** Email + phone + full financial profile (income, debts, net worth, savings) in one row is sensitive PII; the modal promises "your data is only shared with verified advisors." Exposure is gated on Supabase dashboard credentials — fine for now; worth a retention/deletion story if the product relaunches in a GDPR-adjacent market.

**⚪ S4 — Client-side tier gating** (`?demo=1`, localStorage `tier`) is trivially bypassable. Acceptable: there's nothing to steal but UI access, and no payment system exists yet (B5). Don't ship Stripe without moving entitlement server-side.

**⚪ S5 — ErrorBoundary prints raw stack traces** to end users. Minor info disclosure; also a debugging gift. Keep, but consider softening copy on relaunch.

**🟡 Q1 — Duplication hotspots.** The retirement drawdown simulation loop exists three times (engine `revResult`, AchieveTab `baseCoverage` + `simCoverage` — identical bodies); `updatePortAlloc`/`updateContribAlloc` are byte-identical twins; email validation ×3 with one broken copy (B2); and despite a working i18n system, dozens of strings use inline `lang==="en"?"...":"..."` ternaries (Main, AchieveTab, LeadCaptureModal) — two translation mechanisms to maintain.

**⚪ Q2 — Hostile naming.** `mR, fvC, fvL, pvA, gB, mD, uE, aE, rE, uD, aD, rD, uG` — single-purpose minification with zero tests to back any rename/refactor. The engine's logic is good; reading it is archaeology.

**⚪ Q3 — No tests, but one obvious candidate.** `useFinancialEngine` + utils/financial.js are nearly pure functions over a plain store object — the single highest-leverage test target in the codebase. A dozen snapshot cases (the verification numbers in this audit would do) would have caught F1–F3 and protect any reactivation refactor.

**⚪ Q4 — AchieveTab at 41KB is dense but not rotten.** Its weight is JSX (inline styles, bilingual ternaries), not logic. The component-aliasing trick (`const Cd = Card`) and inline style objects inflate it; logic-wise it's the best-structured tab.

---

## Summary verdict

The codebase is healthier than the April audit's framing suggests in two areas — the Zustand store (defensive, versioned, well-partialized) and the security posture (correct RLS, strict CSP, publishable key) are above MVP par. The engine's financial model is conceptually sound with moderate consistency defects (F2, F3) and one dead-but-broken function (F1).

The real problems are **product-functional, not architectural**: the email-capture funnel silently discards every email (B1), one of its two entry points accepts garbage emails (B2), the post-upgrade Dashboard is unreachable from navigation (B3), and repeated list edits across sessions corrupt row IDs (B4). If this project is reactivated, the funnel fixes are hours of work and worth more than any refactor; the architecture debt (half-finished engine-object migration, AR1/AR2) is real but already has a proven target pattern in AchieveTab. Two hygiene items are worth doing *now* despite hibernation: add `.env` to .gitignore (S1) and commit or stash the 7 dirty files.
